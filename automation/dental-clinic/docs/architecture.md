# قرارات التصميم

الملف ده بيشرح **ليه** النظام متبني بالشكل ده، مش بس إزاي. لو هتعدّل حاجة،
اقرا الجزء المتعلق بيها الأول.

---

## 1. الداتابيز هي مصدر الحقيقة، مش الكاليندر

الـ AI agent **بيكتب في Supabase بس**. عمره ما بيكلّم Google Calendar.
التحويل لحدث على تقويم الدكتور بيحصل في workflow منفصل (`02-calendar-sync`)
مشغّل بـ database webhook.

**ليه؟** لو الـ agent كان بيكتب في المكانين، هتبقى عندك كتابة على نظامين من غير
transaction تجمعهم. أول ما الكاليندر يرد بـ 500 بعد ما الحجز اتسجّل في الداتابيز
(أو العكس)، يبقى عندك موعد موجود في مكان ومش موجود في التاني — ومحدش هيلاحظ غير
لما المريض يجي العيادة.

بالشكل الحالي: الحجز إما اتسجّل في Postgres أو لأ. والكاليندر مرآة بتلحق،
ولو فشلت بتتعاد من غير ما الحجز نفسه يضيع.

النتيجة العملية كمان: لو الكاليندر وقع، الحجز شغال. لو Supabase وقعت، النظام
بيرفض يحجز — وده الاتجاه الصح للفشل.

## 2. منع تعارض الحجوزات

ده الجزء اللي **مش** ممكن يتحل بـ prompt engineering.

سيناريو حقيقي: مريضين بيكتبوا في نفس اللحظة، والاتنين اختاروا نفس المعاد.
لو الـ agent بيعمل "شوف فاضي؟ → احجز"، فيه فجوة زمنية بين الخطوتين، والاتنين
هيلاقوا المعاد فاضي والاتنين هيحجزوه.

الحل في `schema.sql`:

```sql
constraint appointments_no_overlap exclude using gist (
    doctor_id with =,
    tstzrange(starts_at, ends_at) with &&
) where (status = 'booked')
```

Postgres نفسه بيرفض أي صف تاني بيتقاطع زمنيًا مع موعد قايم لنفس الدكتور.
مفيش فجوة، ومفيش lock بيتاخد في كود التطبيق.

الـ RPC بيمسك الاستثناء ويرجّع رد **يقدر يتصرّف فيه** بدل ما يفشل:

```json
{ "ok": false, "reason": "slot_taken", "alternatives": [ ... 5 مواعيد ... ] }
```

والـ system prompt بيقول للموديل صراحة: لما تشوف `slot_taken`، اعرض البدائل
على طول ومتعيدش نفس المحاولة.

لاحظ الشرط `where (status = 'booked')`: الإلغاء بيغيّر الحالة، فالصف بيخرج من
القيد والمعاد يرجع متاح تلقائيًا. مفيش صفوف بتتمسح.

**اختبار 7 و 14** في `test_flow.sql` بيغطّوا الحالتين دول.

## 3. الموديل مش مسموح له يخترع معاد

كل المواعيد اللي الـ agent بيعرضها لازم تكون راجعة من `available_slots()`،
وهي دالة SQL بتولّد الـ slots من:

- مواعيد عمل الدكتور وأيامه (`work_start`, `work_end`, `work_days`)
- مدة الخدمة المطلوبة
- طرح أي وقت متحجوز فعلًا
- استبعاد أي معاد أقرب من 30 دقيقة من دلوقتي

الموديل بيشوف نتيجة جاهزة، فمش محتاج يحسب حاجة — وده بيقلّل مساحة الخطأ
لأقصى درجة. الـ prompt بيمنع اختراع المواعيد، لكن الـ RPC هو اللي بيضمن إن
أي معاد مخترع هيترفض على أي حال (`outside_working_hours`).

**الدفاع بطبقتين مقصود:** الـ prompt بيمنع الغلط، والداتابيز بترفضه.

## 4. رقم التليفون مش بياخده الموديل

كل أداة محتاجة رقم التليفون بتاخده من عقدة `Normalize Message` عن طريق
expression، مش كـ placeholder الموديل بيملاه:

```json
"p_phone": "{{ $('Normalize Message').first().json.phone }}"
```

**ليه؟** لأن `patient_history` و `cancel_appointment` و `reschedule_appointment`
بيستخدموا الرقم كإثبات ملكية. لو الرقم كان من الموديل، أي مريض يكتب
"رقمي 01xxxxxxxxx" ويقرا سجل حد تاني أو يلغّي مواعيده.

الرقم بييجي من قناة الشات نفسها، والموديل مش بيلمسه.
**اختبار 9** بيتحقق إن رقم غلط بيرجّع `appointment_not_found`.

## 5. مزامنة الكاليندر قابلة لإعادة التشغيل

`02-calendar-sync` بيقرا الصف من الداتابيز تاني بدل ما يعتمد على الـ payload،
وبيقرر بناءً على وجود `google_event_id`:

| الحالة                                        | التصرف                   |
| --------------------------------------------- | ------------------------ |
| `booked` من غير `google_event_id`             | إنشاء حدث → حفظ الـ id   |
| `booked` ومعاه `google_event_id` وتغيّر الوقت | تحديث الحدث              |
| `cancelled` ومعاه `google_event_id`           | حذف الحدث → تفريغ الـ id |

يعني لو الـ webhook اتبعت مرتين، أو أعدت تشغيل execution فشلت، مش هتلاقي
حدثين لنفس الموعد. عقدة الحذف متظبّطة على `continueRegularOutput` عشان حدث
اتمسح من الكاليندر يدويًا ميوقفش الـ workflow.

## 6. حلقة المتابعة والآراء

الجزء اللي بيخلّي النظام مش بينتهي عند الحجز.

كل خميس 6 مساءً:

1. `mark_past_appointments_completed()` — أي موعد عدّى ومتلغاش يتحوّل لـ `completed`.
   من غير الخطوة دي، مفيش حاجة بتقول "الزيارة حصلت".
2. `visits_pending_feedback(7)` — زيارات آخر ٧ أيام اللي **لسه** متسألوش.
3. الموديل بيكتب رسالة متابعة مخصّصة لكل مريض.
4. تتبعت على Gmail لو عنده إيميل، وإلا على قناة الشات.
5. `mark_feedback_requested()` بتختم المواعيد اللي اتبعتت.

الخطوة الأخيرة هي اللي بتمنع إن مريض يتسأل نفس السؤال كل أسبوع. عمود
`feedback_requested_at` بيتحدّث بس لما يكون `null`، فحتى لو الـ workflow اشتغل
مرتين بالغلط، الرسالة بتتبعت مرة واحدة.

الرد بيدخل على `04-feedback-intake`، والموديل بيطلّع JSON منظّم:

```json
{ "rating": 2, "sentiment": "negative", "summary": "...", "topics": ["الانتظار"], "is_complaint": true }
```

ولو `is_complaint = true`، الـ RPC بيفتح صف في `complaints` جوه نفس الـ transaction
بتاعة تسجيل الرأي، والإدارة بتاخد إيميل في نفس اللحظة. **اختبار 13** بيغطّي ده.

## 7. الأمان

- **RLS مفعّل** على `patients` و `appointments` و `complaints` و `feedback`
  و `n8n_chat_histories` **من غير أي policy تصريحية**. يعني أي مفتاح
  `anon` أو `authenticated` — حتى لو اتسرّب من متصفح — مش هيقرا ولا صف.
  n8n بيتصل بـ `service_role` اللي بيتخطّى الـ RLS.
- الأطباء والخدمات بس مقروءين للعامة، عشان تقدر تعمل صفحة حجز عامة لو حبيت.
- كل الـ RPCs `security definer` و `set search_path = public`، فمش ممكن
  تتخطف بـ search_path مزوّر.
- الـ system prompt بيمنع طلب أي بيانات دفع.

## 8. حدود النظام الحالي

حاجات مقصود إنها مش موجودة — ضيفها لما تحتاجها:

- **مفيش تحقق من الهوية.** رقم التليفون هو الإثبات الوحيد. كفاية لعيادة،
  مش كفاية لبيانات طبية حسّاسة. لو محتاج أكتر، ضيف OTP قبل `patient_history`.
- **مفيش تذكير قبل الموعد.** سهل تضيفه: schedule trigger + استعلام على
  المواعيد بكرة. مكانش ضمن المطلوب.
- **مفيش قائمة انتظار.** لما معاد يتلغي، محدش بيتبلّغ إنه فضي.
- **الكاليندر اتجاه واحد.** لو موظف عدّل حدث من Google Calendar مباشرة،
  التعديل مش هيرجع للداتابيز. خلّي التعديلات كلها تعدّي على النظام.
- **صفوف مرضى من محاولات فاشلة.** `book_appointment` بيعمل upsert للمريض قبل
  ما يحاول يحجز، فمحاولة فشلت بتسيب سجل مريض. ده مقصود — بيانات المريض
  بتتحفظ حتى لو الحجز مكملش — بس خد بالك لو بتحسب معدل التحويل.
