# نشر النظام على Vercel

دليل عملي من الصفر حتى يعمل الموقع على الإنترنت ويصل إليه المركز والمرضى.

---

## قبل أن تبدأ: ما الذي سترفعه فعلًا

هذا النظام يحتوي **بيانات مرضى**: أسماء وأرقام هواتف وتشخيصات وحسابات مالية. رفعه على الإنترنت
يعني أن هذه البيانات تصبح على خوادم شركة أمريكية (Vercel) وقاعدة بيانات مستضافة (Upstash).

- النظام محمي بتسجيل دخول، والصلاحيات مفروضة على السيرفر لا في الواجهة فقط.
- كلمات السر ومفاتيح بوابة المريض كلها مُجزّأة ولا تُخزَّن كنص.
- لكن **مسؤولية البيانات تبقى عليك**: من يملك حساب Vercel يملك الوصول لقاعدة البيانات.

لو كان هذا غير مقبول لمركزك، البديل الجاهز في المشروع هو تشغيله على جهاز داخل المركز
(انظر README: «تشغيل نسخة السيرفر داخل المركز»)، أو استئجار سيرفر خاص تتحكم فيه بالكامل.

## الخطوات

### 1. قاعدة البيانات (Upstash Redis)

نظام ملفات Vercel للقراءة فقط، فلا يمكن حفظ البيانات في ملف. نستخدم Upstash Redis عبر REST.

1. ادخل [console.upstash.com](https://console.upstash.com) وسجّل بحساب GitHub.
2. **Create Database** → اختر النوع **Redis**.
3. الاسم: `clinic` مثلًا. **المنطقة (Region): اختر الأقرب لمصر** — `eu-central-1` (فرانكفورت)
   أو `eu-west-1`. المنطقة البعيدة تعني بطئًا محسوسًا في كل شاشة.
4. الخطة المجانية تكفي للبداية (انظر «الحدود» في آخر الملف).
5. بعد الإنشاء، من صفحة القاعدة انسخ من قسم **REST API**:
   - `UPSTASH_REDIS_REST_URL`
   - `UPSTASH_REDIS_REST_TOKEN`

> انسخ `REST URL` و`REST TOKEN` تحديدًا — لا رابط `redis://`، فالكود يستخدم واجهة REST.

### 2. المشروع على Vercel

1. ادخل [vercel.com/new](https://vercel.com/new) وسجّل بحساب GitHub.
2. **Import** المستودع `mackelw/astro-platform-starter`.
3. Vercel يتعرّف على Astro تلقائيًا — **لا تغيّر أمر البناء ولا مجلد الإخراج**.
4. قبل الضغط على Deploy، افتح **Environment Variables** وأضف المتغيرين:

| الاسم                      | القيمة             |
| :------------------------- | :----------------- |
| `UPSTASH_REDIS_REST_URL`   | الرابط من الخطوة 1 |
| `UPSTASH_REDIS_REST_TOKEN` | الرمز من الخطوة 1  |

أضفهما للبيئات الثلاث (Production و Preview و Development).

5. **Deploy**. بعد دقيقتين يعطيك رابطًا مثل `اسم-المشروع.vercel.app`.

> لو نسيت المتغيرين ستظهر رسالة عربية واضحة تطلب إضافتهما — أضفهما ثم
> **Deployments ← ⋯ ← Redeploy**. التغيير في المتغيرات لا يسري إلا بنشر جديد.

### 3. أول تشغيل

افتح الرابط. سيطلب النظام **إنشاء حساب المدير** مرة واحدة فقط:

- اختر كلمة سر قوية — هذا الحساب يرى كل شيء بما فيه الحسابات المالية.
- بعدها أضف باقي الموظفين من: الإعدادات ← المستخدمون والصلاحيات.

> **هذه الشاشة تظهر لأول من يفتح الرابط، أيًّا كان.** لا ترسل الرابط لأحد قبل أن تُنشئ
> حساب المدير بنفسك.

### 4. النطاق (اختياري)

من **Settings ← Domains** أضف نطاقك (`clinic-reng.com` مثلًا) واتبع تعليمات ضبط DNS.
الشهادة (HTTPS) تُصدَر تلقائيًا. النطاق المخصص يجعل رابط المريض أقصر وأكثر مصداقية
على واتساب من رابط `vercel.app`.

### 5. تحديثات لاحقة

أي دمج على فرع `main` ينشر تلقائيًا خلال دقيقتين. لا حاجة لأي خطوة يدوية.

## النسخة الاحتياطية (رابط الطوارئ)

الفكرة: **رابطان مختلفان يفتحان نفس بيانات المركز**. لو تعطّل الأول — نشر مكسور، مشكلة في
مشروع Vercel، خطأ بشري في الإعدادات — يفتح المركز الرابط الثاني ويكمل يومه بكل المرضى
والمواعيد كما هي.

> **النسخة التي لها قاعدة بيانات منفصلة ليست احتياطية.** ستفتحها يوم العطل فتجدها فارغة.
> شرط النجاح الوحيد: **نفس متغيرَي Upstash في المشروعين**.

### الإعداد

|                   | الأساسية       | الطوارئ                              |
| :---------------- | :------------- | :----------------------------------- |
| مشروع Vercel      | `rangeclinic2` | مشروع ثانٍ (`rangeclinic-sos` مثلًا) |
| Production Branch | `main`         | `stable`                             |
| متغيرا Upstash    | **نفس القيم**  | **نفس القيم**                        |
| متى يتغير         | مع كل تحديث    | لما تقرر أنت                         |

خطوات إنشاء مشروع الطوارئ:

1. [vercel.com/new](https://vercel.com/new) ← استورد نفس المستودع ← سمِّه `rangeclinic-sos`.
2. أضف **نفس** `UPSTASH_REDIS_REST_URL` و `UPSTASH_REDIS_REST_TOKEN` المستخدمَين في الأساسية.
3. بعد أول نشر: **Settings ← Git ← Production Branch** ← غيّره إلى `stable` ← ثم **Redeploy**.
4. اكتب الرابطين على ورقة في الاستقبال. الرابط الثاني لا يُستخدم إلا وقت العطل.

### تحديث فرع الطوارئ

`stable` متجمد عمدًا. بعد أن تجرّب تحديثًا على الأساسية أيامًا وتطمئن له، انقل `stable` إليه:

```bash
git fetch origin
git checkout stable
git merge --ff-only origin/main
git push origin stable
```

لو رفض `--ff-only` فمعناه أن `stable` فيه شيء ليس على `main` — راجع قبل أن تُجبره.

### لماذا لا يضر اختلاف النسختين على نفس القاعدة

النسختان تقرآن وتكتبان نفس المستند. لو أضاف `main` جدولًا جديدًا لا يعرفه `stable`، كانت
أول كتابة من نسخة الطوارئ ستمحو الجدول بالكامل — **كارثة صامتة**، لأن كل شيء يبدو سليمًا.

لذلك تحافظ دالة `normalize` على أي مفتاح لا تعرفه بدل حذفه، ولا تُنزِّل رقم الإصدار.
يفحص ذلك أمر مخصص:

```bash
npm run check:compat
```

**حدّ هذا الضمان:** يحمي من _إضافة_ جداول وحقول. لا يحمي لو غيّرت نسخة أحدث **معنى** حقل
قائم (وحدة السعر مثلًا) — عندها ستكتب النسخة القديمة قيمًا بالمعنى القديم. فلا تترك `stable`
متأخرًا شهورًا؛ حدّثه بعد كل تحديث تطمئن له.

## النسخ الاحتياطي — لا تؤجّله

**لا يوجد نسخ احتياطي تلقائي على الخطة المجانية من Upstash.** بيانات المرضى في مفتاح واحد،
وحذفه بالخطأ يعني ضياع كل شيء.

من داخل النظام: **الإعدادات ← نسخة احتياطية** تُنزّل ملف JSON بكل البيانات.
اجعلها عادة أسبوعية على الأقل، واحفظ الملف خارج جهاز واحد.

## الحدود التي يجب أن تعرفها

### حجم قاعدة البيانات

القاعدة كلها **مستند JSON واحد** يُقرأ ويُكتب بالكامل في كل تعديل. الأحجام الفعلية المقيسة:

| السجل             | الحجم التقريبي |
| :---------------- | :------------- |
| مريض              | ~280 بايت      |
| تمرين في المكتبة  | ~340 بايت      |
| برنامج منزلي      | ~670 بايت      |
| يوم في سجل المريض | ~240 بايت      |
| جلسة أو دفعة      | ~250 بايت      |

مركز بـ 300 مريض و5000 جلسة و10000 يوم التزام ≈ **3 ميجابايت**. هذا يعمل، لكنه يعني أن كل
تعديل ينقل 3 ميجابايت ذهابًا وإيابًا. عمليًا:

- **حتى ~1 ميجابايت**: سريع ومريح.
- **1 إلى 5 ميجابايت**: يعمل مع بطء محسوس عند الحفظ.
- **فوق 5 ميجابايت**: حان وقت الانتقال لقاعدة بيانات حقيقية (Postgres مثلًا) بجداول منفصلة
  بدل مستند واحد. هذا تغيير في طبقة التخزين وحدها (`src/server/db.ts`) ولا يمس بقية النظام.

راقب الحجم من لوحة Upstash (**Data Size**). المؤشر العملي: لو صار الحفظ بطيئًا، افحص الحجم.

### عدد الطلبات

الخطة المجانية من Upstash تعطي **500 ألف أمر يوميًا**. النظام يحدّث الشاشة كل 30 ثانية للمستخدم
المفتوح، أي ~120 قراءة في الساعة لكل جهاز. خمسة موظفين ثماني ساعات ≈ 5000 أمر يوميًا — بعيد جدًا
عن الحد. عشرات المرضى على البوابة لا يقتربون منه أيضًا.

### الكتابة المتزامنة

Vercel يشغّل **عدة نسخ من الخادم في وقت واحد**. بدون حماية، تعديلان في نفس اللحظة يمحو
أحدهما الآخر (وقد اختُبر ذلك فعلًا: من 12 كتابة متزامنة وصلت 8 فقط). لذلك يأخذ الكود
**قفلًا موزَّعًا** في Redis حول كل دورة قراءة-تعديل-كتابة، فلا تضيع كتابة.

القفل عمره 15 ثانية ويُحرَّر فور انتهاء العملية، فلو تعطلت نسخة وهي ممسكة به انتهى وحده
بدل أن يجمّد المركز. ولو كان الخادم مشغولًا فعلًا تظهر رسالة عربية تطلب المحاولة بعد لحظات.

> **ملاحظة لمن ينشر على Netlify بدلًا من ذلك:** مسار Netlify Blobs في الكود لا يملك هذا القفل،
> لأن `@netlify/blobs@8` لا يدعم الكتابة الشرطية. النشر على Netlify صالح لمركز بمستخدم أو
> مستخدمَين، لكن Vercel + Upstash هو المسار المحمي من هذه المشكلة.

## حل المشكلات

| ما تراه                                     | السبب والحل                                                                             |
| :------------------------------------------ | :-------------------------------------------------------------------------------------- |
| «لم يتم ضبط قاعدة البيانات…»                | المتغيران غير مضبوطين أو لم يُعَد النشر بعد إضافتهما. أضفهما ثم Redeploy.               |
| «تعذر الوصول للمخزن (401)»                  | الرمز خطأ أو منسوخ ناقصًا. انسخ `REST TOKEN` كاملًا من جديد.                            |
| «تعذر قراءة البيانات من المخزن»             | القاعدة موقوفة في Upstash، أو المنطقة غير متاحة مؤقتًا. افحص لوحة Upstash.              |
| الموقع بطيء في كل شاشة                      | منطقة Upstash بعيدة عن مصر. أنشئ قاعدة في `eu-central-1` وانقل النسخة الاحتياطية إليها. |
| «الخادم مشغول بحفظ تعديل آخر»               | ضغط متزامن عالٍ لحظيًا. أعد المحاولة؛ لو تكرر باستمرار فالقاعدة كبرت وحان وقت الانتقال. |
| شاشة إنشاء حساب المدير تظهر رغم وجود حسابات | الموقع متصل بقاعدة أخرى (متغيرات بيئة مختلفة بين Production و Preview). وحّدهما.        |

## قائمة تحقق قبل تسليم الرابط للمركز

- [ ] أنشأتُ حساب المدير بنفسي قبل إرسال الرابط لأي أحد
- [ ] كلمة سر المدير قوية وغير مشتركة مع أحد
- [ ] أضفتُ حسابًا منفصلًا لكل موظف بدوره الصحيح (استقبال / أخصائي)
- [ ] جرّبتُ إصدار مفتاح بوابة لمريض تجريبي وفتحته من الموبايل
- [ ] أخذتُ أول نسخة احتياطية وحفظتها خارج الجهاز
- [ ] ضبطتُ تذكيرًا أسبوعيًا بالنسخ الاحتياطي
